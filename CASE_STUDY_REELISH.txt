REELISH
IN-DEPTH PRODUCT CASE STUDY

Project type: Cross-platform media discovery and playback app
Platform: Flutter application
Project naming: The repository is named Onfeed; the application title and README identify the product as Reelish. This case study uses Reelish (Onfeed) to make that naming clear.

OVERVIEW

Reelish brings entertainment discovery, personal watch tracking, and stream playback into one dark, cinematic interface. People can browse and search a TMDB-powered catalog, explore title and episode details, configure compatible provider add-ons, find available streams, and continue playback with subtitles and personalized player settings. The product is a catalog and playback client: catalog data, add-ons, streams, subtitles, and artwork come from external services and providers.

THE PROBLEM

The viewing journey is fragmented. Someone may discover a movie in one catalog, look up its details elsewhere, check multiple providers for a playable source, then switch again to watch it. The experience becomes especially awkward for TV series, where season and episode selection, source choice, subtitle configuration, and remembering progress all matter.

There is also a product and engineering challenge behind the interface: source availability depends on independently maintained providers and returned URLs. Responses may be incomplete, duplicated, malformed, slow, or unsuitable for playback. A client must coordinate those providers while keeping the user informed, protect itself from untrusted network destinations, and still present a coherent player experience across platforms.

THE SOLUTION

Reelish combines discovery and playback in a single app, while treating catalog metadata and stream providers as separate services.

• Discovery: A home screen brings together trending and popular titles, search, recommendations, new releases, and a featured spotlight. Quality and recency rules rank spotlight and release collections rather than relying on one undifferentiated feed.
• Exploration: Title details include metadata and artwork; series pages load seasons and episodes so users can move from a show to a specific episode.
• Extensible source discovery: Users can install Nuvio-compatible provider manifests, enable or disable individual providers, and discover sources for a title. Stream normalization and validation turn provider results into a consistent set of playable choices.
• Playback: A custom player provides playback controls, stream selection, episode navigation, subtitle selection, and configurable viewing preferences. Supported text subtitles include WebVTT and SRT. Playback settings cover gestures, playback speed, next-episode behavior, language preferences, and subtitle appearance.
• Continuity: A local library keeps favorites and watch history, including saved playback progress. The app can retain a recently used stream for optional reuse.
• Resilience and trust boundaries: TMDB requests use response caching, in-flight request deduplication, bounded concurrency, and retry handling. Provider code runs in a bounded QuickJS environment. Network requests validate public destinations and redirects, while provider-returned sources are normalized and checked before playback.

THE EXPERIENCE FLOW

1. Browse a curated home feed or search the catalog.
2. Open a title to review its synopsis and details; for a series, select a season and episode.
3. Ask the enabled providers for sources and choose an available stream, or use configured automatic selection.
4. Watch with the player controls and subtitle options that fit the viewing setup.
5. Return later through the library and resume from saved progress.

TECH STACK

• Flutter and Dart for the cross-platform application and interface.
• Material widgets with a custom dark glass visual theme, Montserrat typography, and Feather icons.
• TMDB API for catalog, search, metadata, recommendation, season, and episode data; the http package handles API requests.
• Stremio-compatible add-on support documented by the project, plus Nuvio-compatible provider manifests and a locally bundled Cheerio JavaScript bundle for provider compatibility.
• flutter_js with a bundled QuickJS runtime to execute provider scripts in an isolated, resource-bounded environment.
• video_player as the app-facing playback API, with Android video_player/Media3 registration and a local MediaKit adapter available in the project; other platforms use the registered Flutter video player implementation. The player engine is abstracted behind a Dart interface.
• shared_preferences for on-device library, provider, and playback preferences; path_provider for application storage and torrent cache paths.
• http, url_launcher, package_info_plus, and platform-specific Flutter packages for networking, external links, app version information, and playback support.

KEY DESIGN AND ENGINEERING DECISIONS

Keep catalog and playback responsibilities separate. TMDB answers “what should I watch?” while independently configured providers answer “what sources are available?” This lets catalog discovery remain useful even as provider availability changes.

Normalize external results before they reach the player. A consistent stream model and validation path reduce UI complexity and make provider-specific response formats easier to handle.

Bound untrusted provider work. Provider scripts run without direct filesystem or credential access, with limits on execution time, memory, concurrent runtimes, and HTTP payloads. Destinations and redirects are checked before Dart HTTP requests are sent.

Make repeat use local and immediate. Favorites, history, progress, and preferences are stored on device, so the app has a personal library without requiring an account backend.

OUTCOME

The result is a feature-complete client architecture that connects browsing, provider-based source discovery, and playback in one application. Its strongest product contribution is the joined-up viewing flow; its strongest technical contribution is the boundary it creates between a polished client experience and variable external provider behavior.

The repository contains automated Flutter tests for areas including discovery ranking, provider fetching, stream discovery, playback settings and pipeline, app transitions, and network destination validation. No performance, adoption, or user research results are stated here because those figures are not established by the project files.

SCOPE AND LIMITATIONS

Reelish does not host or supply a media library. Availability and quality depend on external catalogs, configured providers, hosts, and networks. The README states that direct HTTP(S) stream URLs supported by the platform player can be played; torrent-only or other non-direct sources require a resolver or compatible backend. Provider repositories are user-configured executable code and are not cryptographically signed by the current repository format. Native playback and torrent networking have limits that are described in docs/streaming_security.md, so the client-side network checks do not mean every native media request is pinned or inspected.

PORTFOLIO SUMMARY

I built Reelish (Onfeed), a Flutter streaming catalog client that connects TMDB discovery with configurable provider-based stream lookup and a customizable video player. I focused on making the end-to-end viewing journey feel coherent while building the service boundaries, local library, playback controls, and safeguards needed to handle variable third-party data.
